# ⚡ doit-optimaize

**근거 기반으로, 동작을 보존하며, 안전하게** 코드를 다듬는 Claude Code · Codex 스킬 모음

성능 핫스팟 · 메모리 · 리팩터링 · 최적화 리뷰 · 로그 레벨 배치 · 테스트 현행화 · 의존 방향 검사를 한곳에서.
특정 언어나 프레임워크에 종속되지 않습니다.

## ✨ 포함된 스킬

| 스킬 | 호출 | 하는 일 |
|------|------|---------|
| 🔥 `hotspot` | `/optimize:hotspot` | 성능 병목(N+1·중복 연산·비효율 자료구조)을 **영향도 순**으로 찾아 안전하게 최적화 |
| 🧠 `memory` | `/optimize:memory` | 메모리·리소스 절감(전량 적재·누수·미해제 리소스), **트레이드오프 명시** |
| 🧹 `refactor` | `/optimize:refactor` | 중복·복잡도 정리(함수 추출·조기 반환), **동작·시그니처 보존** |
| 🔍 `review` | `/optimize:review` | 최적화 관점 **진단만**(코드 수정 없이) — 위치·문제·영향도·조치·리스크 표 |
| 🛡️ `safe` | `/optimize:safe` | 동작 **100% 보존**을 검증하며 최적화 → 작은 커밋 단위 |
| 📝 `logging` | `/optimize:logging` | `info`·`debug`·`error`를 **적재적소에** — 프로젝트의 기존 로깅 관용구를 학습해 그대로 따름 |
| 🧪 `test` | `/optimize:test` | 테스트 **현행화 + 커버리지 측정**. 테스트가 없으면 환경을 판단해 **추가 여부·범위를 먼저 확인** |
| 🧭 `arch` | `/optimize:arch` | **의존 방향 검사** — 역방향 의존·계층 건너뛰기·순환 참조·기술 누출을 import 사실로 진단 |
| 📑 `apispec` | `/optimize:apispec` | **API 명세 작성·발행** — 마크다운을 원본으로 두고 의존성 없는 단독 HTML 을 함께 생성, 두 산출물 동기화 강제 |

> 각 스킬은 `[파일/함수/범위]`를 인자로 받으며, **비우면 현재 변경분(`git diff`)** 을 대상으로 합니다.
> (`test`·`arch`는 예외로, 비우면 **프로젝트 전체**를 대상으로 합니다.)

```bash
/optimize:hotspot src/main/java/com/example/OrderService.java
/optimize:review           # 현재 변경분 진단
/optimize:logging          # 변경분의 로그 레벨 점검·보강
/optimize:test             # 테스트 현행화 + 커버리지
/optimize:arch             # 의존 방향·순환 참조 검사
```

## 📋 공통 리포트 형식

**모든 스킬은 긴 설명 대신 결론부터, 표로 보고합니다.** 어느 명령·어떤 기준으로 무엇을 했는지가 첫 표에 다 들어갑니다.

> **결론 한 줄** — N+1 2건과 중복 연산 1건을 고쳐 요청당 쿼리를 201건 → 3건으로 줄였습니다.
>
> | 실행 | 대상 | 결과 | 검증 |
> |------|------|------|------|
> | `/optimize:hotspot OrderService.java` | 파일 1개 / `findOrders` 외 2개 | 수정 3건, 보류 1건 | 테스트 128건 통과, 실패 0 |
>
> | # | 위치 | 한 일 | 근거 → 효과 |
> |---|------|-------|-------------|
> | 1 | `OrderService.java:88` | 루프 내 단건 조회 → 배치 조회 | 쿼리 201건 → 2건 |
>
> - 보류: `ReportBuilder:140` — 동작 변경이 필요해 별도 논의

- **`실행` 칸은 받은 인자를 그대로** 적습니다. 인자 없이 호출됐다면 `(인자 없음 → git diff)`처럼 **실제 판단 기준**이 남습니다.
- 표 밖 설명은 **결론 한 줄 + 불릿 3개 이내**. 과정 서술은 붙이지 않습니다.
- 진단 전용 스킬(`review`·`arch`)은 `검증` 대신 `코드 변경: 없음`이 들어가고, 지적이 없으면 표 대신 **"지적 사항 없음" 한 줄**로 끝냅니다.

<details>
<summary><b>📝 <code>logging</code> — 무엇을 하나</b></summary>

<br>

로그를 고치기 전에 **이 프로젝트의 로깅 방식을 먼저 조사**합니다 — 로거 획득 관용구(정적 로거 / `@Slf4j` / 모듈 로거), 메시지 포맷과 파라미터화 방식, 구조적 로깅(MDC·JSON 필드) 여부, 상관관계 ID, 마스킹 유틸, 운영 환경 기본 레벨.

그다음 레벨 기준표에 따라 판정합니다.

| 레벨 | 기준 |
|------|------|
| `ERROR` | 실패했고 **사람의 조사·개입이 필요**한 사건 (알림이 울려도 이상하지 않은 것) |
| `WARN` | 실패는 아니지만 방치하면 문제가 되는 신호 (재시도 성공, 폴백 진입, 임계치 근접) |
| `INFO` | **비즈니스적으로 의미 있는 사건** (상태 전이, 배치 시작/종료, 외부 호출 결과 요약) |
| `DEBUG` | 개발·장애 분석용 내부 흐름과 중간값 (운영에서 꺼져 있어도 되는 것) |

누락(예외를 삼키면서 로그 없음)뿐 아니라 **과잉**(루프 안 로그, 계층마다 중복된 `log`+`throw`, 정상 흐름의 `ERROR`, `print` 잔재)도 함께 정리합니다.
민감정보 원문 출력, 로깅을 위한 추가 쿼리, 새 로깅 라이브러리 도입은 하지 않습니다.

</details>

<details>
<summary><b>🧪 <code>test</code> — 무엇을 하나</b></summary>

<br>

**0단계로 개발 환경을 먼저 파악**합니다 — 빌드 도구, 테스트 프레임워크, 테스트 위치·명명 규칙, 커버리지 도구, CI에 정의된 공식 실행 명령, 레이어 구조.

**테스트가 있으면 → 현행화.** 손대기 전 실패 목록을 기준선으로 잡고, 낡은 기대값·깨진 임포트·건너뛴 테스트·단언 없는 테스트·불안정(flaky) 테스트를 실제 구현의 계약에 맞게 고칩니다. 이후 커버리지를 측정해 **수치와 함께 "어디가 비었는지"** 를 위험도 순으로 보고합니다.

**테스트가 없으면 → 묻고 시작.** 임의로 만들지 않고, 환경 적합성(프레임워크 의존성 유무, 실행 가능 여부, 테스트하려면 프로덕션 코드 수정이 필요한 구조인지)을 판단한 뒤 범위를 확인합니다.

| 범위 | 대상 |
|------|------|
| API 레이어만 | 외부 계약(HTTP/RPC) — 통합·E2E 성격, 회귀 방어가 가장 넓음 |
| 컨트롤러 레이어만 | 요청 매핑·검증·직렬화·상태코드 (하위 계층 모킹) |
| 서비스 레이어만 | 유스케이스·트랜잭션 흐름 (저장소·외부 연동 모킹) |
| 도메인 레이어만 | 엔티티·값 객체·도메인 규칙 — 가장 빠르고 안정적 |
| 전부 | 위 전체 — 레이어별 단계적 진행 |

> ⚠️ 이 스킬은 **프로덕션 코드를 고치지 않습니다.** 테스트가 실제 버그를 잡았다면 기대값을 맞추는 대신 **버그로 보고**합니다.

</details>

<details>
<summary><b>🧭 <code>arch</code> — 무엇을 하나</b></summary>

<br>

> 아키텍처는 문서가 아니라 **import 문에 적혀 있습니다.**

**무엇이 위반인지는 프로젝트가 정합니다.** 일반론으로 판정하지 않고, 먼저 의도된 아키텍처를 조사합니다 — 문서·ADR, **이미 있는 아키텍처 테스트·린트 규칙**(ArchUnit, `dependency-cruiser`, `import-linter`, `deptrac`, ESLint `no-restricted-paths`, Go `internal/`), 빌드 모듈의 의존 선언, 패키지 구조, 다수 관행. 의도를 확정할 수 없으면 **추론한 허용 방향표를 먼저 제시하고 동의를 받은 뒤** 검사합니다.

검사 항목:

| 항목 | 내용 |
|------|------|
| **역방향 의존** | 안쪽(도메인)이 바깥(인프라·웹·프레임워크)을 참조 — 가장 심각, 1순위 |
| **계층 건너뛰기** | 컨트롤러 → 저장소 직접 호출 (규약상 의도적 허용인지 먼저 확인) |
| **순환 의존** | 패키지·모듈·클래스 사이클을 **전체 경로**로 (`a → b → c → a`) |
| **기술 누출** | 도메인에 ORM/직렬화/웹 애노테이션, 엔티티가 API 응답으로 그대로 노출 |
| **DIP 미적용** | 인터페이스를 **사용하는 쪽**이 아니라 구현하는 쪽이 소유 → 방향이 여전히 바깥 |
| **경계 침범 / 공통 모듈 역류** | 다른 컨텍스트의 내부 구현 참조, `common`이 도메인을 참조 |

보고는 **위반 · 방향 · 위치 · 어긴 규칙 · 영향도 · 권장 조치** 표로 내고, `지금 고칠 것 / 나중에 / 의도된 예외`로 나눕니다. 영향도는 "침범 깊이 × 확산 범위 × 대상의 핵심도"로 재고, **한 곳만 고치면 여러 위반이 사라지는 지점**을 맨 위에 올립니다.

> ⚠️ **기본값은 검사입니다.** 구조 변경은 파급이 크고 되돌리기 어려우므로 승인한 항목만, 한 번에 하나씩(DIP로 방향 뒤집기 / 매핑 레이어 / 사이클의 가장 약한 간선 끊기 / 위치 이동) 적용합니다. 채택되지도 않은 아키텍처를 들이대 위반 목록을 만들지 않습니다.

</details>

## 🩺 설치가 안 될 때

<details>
<summary><b><code>ssh: connect to host github.com port 22: Connection timed out</code></b></summary>

<br>

플러그인이나 저장소 문제가 **아닙니다.** 설치하는 환경(일부 WSL·사내망 등)에서 **SSH 22번 포트가 막혀** 있을 때 발생합니다. git이 SSH 대신 HTTPS로 clone하도록 아래 한 줄을 실행한 뒤 다시 설치하면 됩니다.

```bash
git config --global url."https://github.com/".insteadOf "git@github.com:"
```

- 이 설정은 각자 PC의 전역 `~/.gitconfig`에 저장되며, 이후 모든 GitHub clone에 적용됩니다.
- 되돌리려면: `git config --global --unset-all url."https://github.com/".insteadOf`
- SSH 22번이 열린 환경(대부분의 개인 PC)에서는 이 설정 없이도 정상 설치됩니다.

</details>

## 🧭 설계 원칙

모든 스킬이 공유하는 안전장치입니다.

| 원칙 | 내용 |
|------|------|
| **근거 기반** | 추정이 아니라 쿼리 수·복잡도(O표기)·자료구조 같은 **코드 사실**로 판단합니다. |
| **동작 보존** | 관측 가능한 동작과 **공개 시그니처를 바꾸지 않습니다.** |
| **안전 우선** | 테스트 코드와 DB 마이그레이션 파일은 **명시적 지시 없이는 수정하지 않습니다.** (`test` 스킬이 바로 그 "명시적 지시" 경로이며, 반대로 이 스킬은 프로덕션 코드를 건드리지 않습니다.) |
| **영향도 순** | 큰 것부터 고칩니다. 드물게 도는 경로의 미세 최적화로 복잡도만 올리지 않습니다. |
| **검증** | 변경 후 프로젝트 **테스트 스위트로 회귀가 없음**을 확인합니다. |
| **프로젝트 패턴 준수** | 새 관용구를 들여오지 않습니다. 로깅 방식·테스트 스타일·네이밍은 **주변 코드를 먼저 학습해** 그대로 따릅니다. |
| **승인 후 진행** | 새 의존성 추가, 설정 변경, 없던 테스트 신규 작성은 **먼저 묻고** 진행합니다. |
| **두괄식 리포트** | 모든 스킬이 **결론 한 줄 + 표**로 마칩니다. 어느 명령·어떤 기준으로 무엇을 했는지가 한눈에 보입니다. |
