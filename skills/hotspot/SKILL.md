# 성능 핫스팟 최적화

느린 곳을 **추측이 아니라 근거로 찾고**, 영향이 큰 것부터, **동작을 바꾸지 않고** 고친다.
최적화의 실패 대부분은 (1) 병목이 아닌 곳을 고치거나 (2) 고치다 동작이 바뀌는 것이다. 이 스킬은 그 둘을 막는 절차다.

## 진행 순서

1. **범위 확정** — 인자가 있으면 그 대상, 없으면 `git diff`(스테이징 포함)로 현재 변경분을 대상으로 한다. 대상이 모호하면 최적화 전에 확인한다.
2. **후보 수집** — 아래 체크리스트로 의심 지점을 나열한다. 이 단계에서는 판단하지 말고 폭넓게 모은다.
3. **영향도 산정** — 각 후보를 "호출 빈도 × 1회 비용 × 입력 규모(N)"로 가늠해 **큰 것부터** 정렬한다. 하루 한 번 도는 코드의 미세 최적화보다, 요청마다 도는 루프의 N+1이 훨씬 중요하다.
4. **근거 확인** — 상위 후보에 대해 근거를 확보한다(아래 "근거 규칙"). 근거가 약하면 순위를 내리거나 제외한다.
5. **수정** — 상위 항목부터, 동작 보존을 확인하며 고친다. 한 번에 하나씩, 되돌리기 쉬운 단위로.
6. **검증** — 프로젝트 테스트 스위트를 실행해 회귀가 없음을 확인한다. 가능하면 최적화 대상의 지표(쿼리 수·처리 시간·할당량)가 실제로 개선됐음을 수치로 보인다.

## 무엇을 찾나 (언어 무관 체크리스트)

- **N+1 / 반복 I/O** — 루프 안에서 쿼리·네트워크·파일 접근이 반복되는가? 배치 조회·조인·프리패치·캐시로 1회로 줄일 수 있는가?
- **중복·불필요 연산** — 루프 안에서 매번 같은 값을 재계산하는가(루프 밖으로 끌어올리기)? 같은 데이터를 여러 번 순회하는가?
- **비효율 자료구조·알고리즘** — 반복 조회에 리스트 선형 탐색을 쓰는가(→ Set/Map)? 불필요한 O(n²)가 있는가? 정렬·중복 제거를 매번 다시 하는가?
- **과도한 객체 생성·할당** — 뜨거운 경로에서 큰 임시 객체·문자열 접합·박싱을 반복하는가?
- **게으르게 해도 될 즉시 계산** — 항상 필요하지 않은 값을 항상 계산하는가? 짧게 끝낼 수 있는 조건을 뒤늦게 검사하는가(단락 평가)?
- **경계에서의 과다 전송** — API·DB에서 필요보다 많은 컬럼/행/필드를 가져오는가?

## 근거 규칙 (추정 금지)

지적과 수정안에는 반드시 **관측 가능한 근거**를 붙인다:

- N+1은 "루프 N회 × 쿼리 1건 = N+1건" 처럼 **쿼리 수**로 설명한다.
- 알고리즘 개선은 **복잡도**로 설명한다(예: O(n²) → O(n)).
- "빨라질 것 같다"는 근거가 아니다. 코드에서 확인되는 사실만 쓴다. 확인이 필요하면 프로파일·쿼리 로그·벤치마크로 확인하고, 못 하면 "미검증 가설"로 표시한다.

## 안전 제약

- **관측 가능한 동작을 바꾸지 않는다.** 출력, 부수효과, 공개 시그니처, 정렬 순서, 예외 동작이 그대로여야 한다.
- **테스트 코드와 DB 마이그레이션 파일은 명시적 지시 없이는 수정하지 않는다.** 최적화가 테스트를 깨면 테스트가 아니라 내 변경을 먼저 의심한다.
- 주변 코드의 컨벤션(네이밍·주석 밀도·관용구)에 맞춘다.

## 출력

수정 전에 먼저 **영향도 순 요약**을 제시한다: 각 항목의 위치, 근거(쿼리 수·복잡도), 제안 수정, 예상 효과. 그다음 사용자가 동의한 상위 항목부터 적용하고, 각 적용 후 검증 결과를 보고한다.
