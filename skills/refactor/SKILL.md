# 동작 보존 리팩터링

리팩터링은 **동작을 그대로 둔 채 구조만 개선**하는 작업이다. 새 기능도, 버그 수정도, 성능 변경도 아니다.
그 경계를 지키는 것이 이 스킬의 전부다 — 무언가 동작이 바뀐다면 그건 리팩터링이 아니라 별도 작업이다.

## 진행 순서

1. **범위 확정** — 인자가 있으면 그 대상, 없으면 `git diff`로 현재 변경분을 대상으로 한다.
2. **냄새 식별** — 아래 체크리스트로 개선 지점을 찾는다.
3. **작은 단위로 변형** — 한 번에 하나의 변형만 적용한다. 여러 개를 뭉쳐 바꾸면 무엇이 동작을 깼는지 못 짚는다.
4. **매 단계 검증** — 변형마다 프로젝트 테스트 스위트로 동작이 그대로임을 확인한다.

## 무엇을 고치나 (언어 무관 체크리스트)

- **중복 로직** — 반복되는 패턴·복붙 블록을 함수/헬퍼로 추출한다. 단, "우연히 비슷한" 코드까지 억지로 합쳐 결합도를 높이지 않는다. 진짜 같은 개념일 때만 합친다.
- **깊은 중첩** — 조기 반환(early return)·가드 절로 화살표형 중첩을 편다. 예외/경계 조건을 앞에서 처리하고 본문을 평평하게.
- **긴 함수** — 하나의 함수가 여러 일을 하면 의미 단위로 쪼갠다. 각 함수는 이름만으로 무엇을 하는지 드러나야 한다.
- **불명확한 네이밍** — 의도를 드러내는 이름으로 바꾼다. 좋은 이름은 주석을 대체한다.
- **매직 값·중복 상수** — 흩어진 리터럴을 이름 있는 상수로 모은다.
- **죽은 코드** — 도달 불가·미사용 코드는 제거한다(단, 공개 API·리플렉션·동적 참조 여부를 먼저 확인).

## 안전 제약 (동작·시그니처 보존)

- **공개 API 시그니처를 바꾸지 않는다.** 파라미터·반환 타입·이름·예외를 그대로 둔다. 시그니처를 바꾸고 싶다면 그건 리팩터링이 아니므로 먼저 사용자에게 알린다.
- **관측 가능한 동작을 바꾸지 않는다.** 반환값, 부수효과, 예외, 로그/이벤트 등 외부에서 보이는 것은 동일해야 한다.
- **테스트 코드와 DB 마이그레이션 파일은 명시적 지시 없이는 수정하지 않는다.** 리팩터링이 테스트를 깨면 테스트가 아니라 내 변경을 먼저 의심하고 사용자에게 보고한다.
- **주변 코드의 컨벤션(네이밍·주석 밀도·관용구)에 맞춘다.** 리팩터링 결과가 주변과 이질적이면 오히려 가독성을 해친다.

## 출력

작업 **중에는** 무엇을 왜 정리하는지 짧게 밝히고 작은 단위로 적용한다.
작업 **후에는** 아래 최종 리포트만 남긴다.

## 최종 리포트 (형식 고정)

작업이 끝나면 **결론 한 줄 + 표**로만 보고한다. 과정 설명·산문 문단을 덧붙이지 않는다.

**결론 한 줄** — 무엇을 몇 건 정리했고 동작은 그대로인지.

| 실행 | 대상 | 결과 | 검증 |
|------|------|------|------|
| `/optimize:refactor <받은 인자 그대로>` | 파일 2개 / `PriceCalculator` 외 | 변형 4건 | 테스트 96건 통과, 실패 0 / 시그니처 변경 없음 |

| # | 위치 | 변형 | 효과 |
|---|------|------|------|
| 1 | `PriceCalculator.java:30` | 중첩 4단 → 가드 절로 조기 반환 | 중첩 4 → 1 |

- 동작·시그니처 변경이 필요해 **손대지 않은 개선점**이 있으면 한 줄씩 최대 3개로 별도 제안한다. 없으면 이 불릿을 생략한다.

인자 없이 호출됐으면 `실행` 칸은 `/optimize:refactor (인자 없음 → git diff)`처럼 **실제 판단 기준을 그대로** 적는다.
