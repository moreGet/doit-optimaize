# 메모리·리소스 최적화

메모리 문제는 대개 **"필요한 만큼이 아니라 전부를 붙잡고 있어서"** 생긴다.
전량 적재를 스트리밍으로, 무한히 자라는 캐시를 유계로, 놓친 리소스를 확실히 닫는 것이 핵심이다.

## 진행 순서

1. **범위 확정** — 인자가 있으면 그 대상, 없으면 `git diff`로 현재 변경분을 대상으로 한다.
2. **후보 수집** — 아래 체크리스트로 의심 지점을 나열한다.
3. **영향도 산정** — "보유량 × 지속 시간 × 동시 개수"로 가늠한다. 요청마다 전체 테이블을 힙에 올리는 코드가, 잠깐 쓰는 작은 버퍼보다 훨씬 위험하다.
4. **수정** — 큰 것부터, 동작을 보존하며 고친다.
5. **검증** — 프로젝트 테스트 스위트로 회귀가 없음을 확인한다. 가능하면 개선 효과(피크 메모리·핸들 수)를 근거로 보인다.

## 무엇을 찾나 (언어 무관 체크리스트)

- **전량 적재 → 스트리밍/페이지네이션** — 결과 전체를 리스트로 모아 반환/처리하는가? 커서·스트림·청크·페이지 단위로 흘려보낼 수 있는가? 특히 크기가 입력에 비례해 커지는 컬렉션을 주시한다.
- **닫히지 않는 리소스** — 파일·소켓·DB 커넥션·스트림이 예외 경로에서도 확실히 닫히는가? 언어의 자동 해제 관용구(try-with-resources, `using`, `defer`, `with`, RAII 등)를 쓰는가?
- **메모리 누수** — 정적/전역 컬렉션에 계속 쌓기만 하고 비우지 않는가? 리스너·콜백·캐시 항목이 제거되지 않아 참조가 남는가?
- **무계 캐시** — 상한(크기·TTL) 없는 캐시가 무한히 자라는가? 정말 캐시가 필요한가, 아니면 매번 계산이 더 싼가?
- **불필요한 중간 복사·버퍼** — 같은 데이터를 여러 자료구조로 복제하는가? 통째로 읽어 다시 통째로 쓰는 대신 흘려보낼 수 있는가?
- **과대 보존 범위** — 잠깐 쓸 데이터를 오래 붙잡아 GC를 막는가? 스코프를 좁혀 조기 해제할 수 있는가?

## 트레이드오프 명시 (이 스킬의 핵심)

메모리 절감은 종종 속도나 복잡도와 맞바꾼다. **트레이드오프가 있으면 숨기지 말고 명시하고 기본값을 추천**한다:

- 예: "전량 정렬 후 반환 → 스트리밍 병합으로 바꾸면 피크 메모리는 O(n)→O(1)에 가깝지만, 코드가 복잡해지고 임의 접근이 불가해집니다. 대상이 대용량이므로 스트리밍을 기본 추천합니다."
- 데이터 규모가 작아 문제가 안 되는 곳까지 스트리밍으로 바꿔 복잡도만 올리는 것은 지양한다. **큰 것만 고친다.**

## 안전 제약

- **관측 가능한 동작을 유지한다.** 반환값·순서·부수효과가 그대로여야 한다.
- **테스트 코드와 DB 마이그레이션 파일은 명시적 지시 없이는 수정하지 않는다.**
- 주변 코드의 컨벤션을 따른다.

## 출력

수정 **전에는** 영향도 순 요약과 각 항목의 트레이드오프를 제시하고 동의를 받는다.
수정 **후에는** 아래 최종 리포트만 남긴다.

## 최종 리포트 (형식 고정)

작업이 끝나면 **결론 한 줄 + 표**로만 보고한다. 과정 설명·산문 문단을 덧붙이지 않는다.

**결론 한 줄** — 무엇을 몇 건 고쳤고 메모리가 어떻게 줄었는지.

| 실행 | 대상 | 결과 | 검증 |
|------|------|------|------|
| `/optimize:memory <받은 인자 그대로>` | 파일 2개 / `ReportExporter` 외 | 수정 2건, 보류 1건 | 테스트 96건 통과, 실패 0 |

| # | 위치 | 한 일 | 효과 | 트레이드오프 |
|---|------|-------|------|--------------|
| 1 | `ReportExporter.java:44` | 전량 적재 → 커서 스트리밍 | 피크 메모리 O(n) → O(1) | 임의 접근 불가, 코드 복잡도 소폭 증가 |

- 보류·미적용·확인 필요 항목이 있으면 **한 줄씩 최대 3개**. 없으면 이 불릿을 생략한다.

인자 없이 호출됐으면 `실행` 칸은 `/optimize:memory (인자 없음 → git diff)`처럼 **실제 판단 기준을 그대로** 적는다.
