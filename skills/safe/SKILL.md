# 안전 최적화 (동작 100% 보존)

빠르게 만드는 것보다 **깨뜨리지 않는 것**이 우선인 코드를 위한 절차다.
핵심 아이디어: 먼저 "동작이 바뀌면 즉시 알 수 있는 그물"을 치고, 그 그물이 초록불인 상태에서만 손을 댄다. 그물 없이 하는 최적화는 안전하지 않다.

## 진행 순서 (순서를 지키는 것이 이 스킬의 전부)

1. **범위와 계약 파악** — 대상의 입력·출력·부수효과·예외 등 "관측 가능한 동작"이 무엇인지 먼저 규정한다.
2. **검증 그물 확보** —
   - 기존 테스트가 이 동작을 충분히 덮으면 그걸 근거로 삼는다.
   - 부족하면 **특성화 테스트(characterization test)**, 즉 "현재 동작을 있는 그대로 고정하는 테스트"가 필요하다. **테스트 추가는 명시적 지시가 필요하므로**, 커버리지가 부족하면 임의로 추가하지 말고 사용자에게 "이 부분을 안전하게 하려면 검증용 테스트가 필요합니다. 추가할까요?"라고 먼저 묻는다.
   - 자동 테스트가 어려우면 대표 입력에 대한 변경 전/후 출력 비교(골든 값)를 대안으로 제시한다.
3. **그물이 초록불임을 확인** — 최적화 전에 검증이 통과하는 상태를 먼저 만든다.
4. **작은 단위로 최적화** — 되돌리기 쉬운 작은 변형 하나씩. 각 단위는 독립적으로 커밋 가능한 크기로.
5. **매 단계 재검증** — 변형마다 그물을 다시 돌려 초록불을 확인한다. 하나라도 빨간불이면 **그 변형을 되돌리고** 원인을 분석한 뒤 다시 시도한다.

## 절대 규칙

- **공개 동작·시그니처를 바꾸지 않는다.** 반환값·순서·부수효과·예외·공개 API가 전부 동일해야 한다. 동작을 바꿔야 최적화가 가능하다면, 그건 이 스킬의 범위가 아니므로 먼저 사용자에게 알린다.
- **테스트 코드와 DB 마이그레이션 파일은 명시적 지시 없이는 수정하지 않는다.** 검증용 테스트 추가가 필요하면 반드시 먼저 물어본다.
- **불확실하면 멈추고 묻는다.** 안전이 목적인 작업에서 "아마 괜찮을 것"은 충분하지 않다.

## 출력

작업 **중에는** 단계마다 무엇을 적용했고 그물이 초록불인지 짧게 알린다.
작업 **후에는** 아래 최종 리포트만 남긴다.

## 최종 리포트 (형식 고정)

작업이 끝나면 **결론 한 줄 + 표**로만 보고한다. 과정 설명·산문 문단을 덧붙이지 않는다.

**결론 한 줄** — 무엇을 최적화했고 동작 보존이 무엇으로 확인됐는지.

| 실행 | 대상 | 검증 그물 | 결과 |
|------|------|-----------|------|
| `/optimize:safe <받은 인자 그대로>` | `SettlementService.calculate` | 기존 테스트 24건 + 골든 값 비교 | 변형 3건 전부 초록불, 되돌림 1건 |

| # | 변형 | 검증 | 판정 |
|---|------|------|------|
| 1 | 중복 조회 결과 재사용 | 테스트 24건 통과 | 유지 |
| 2 | 정렬 제거 | 테스트 2건 실패 → 순서 계약 위반 | **되돌림** |

- 승인이 필요한 사항(특성화 테스트 추가 등)이나 미해결 항목이 있으면 한 줄씩 최대 3개. 없으면 생략한다.
