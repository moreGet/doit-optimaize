# 의존 방향 검사

아키텍처는 문서가 아니라 **import 문에 적혀 있다.** 이 스킬은 코드가 실제로 어느 방향을 향하고 있는지를 사실로 확인한다.

의존 방향이 무너지면 증상이 늦게, 그리고 비싸게 온다 — 도메인 규칙을 고치는 데 DB 스키마가 걸리고, 모듈 하나를 떼어내려는데 순환이 딸려 오고, 테스트를 짜려면 프레임워크를 통째로 띄워야 한다. 그래서 **고치기보다 먼저 재는 것**이 이 스킬의 기본값이다.

## 0단계: 의도된 아키텍처 파악 (반드시 먼저)

**무엇이 위반인지는 프로젝트가 정한다.** 일반론으로 판정하지 않는다. 아래를 조사해 "이 프로젝트가 지키려는 방향"을 먼저 확정한다.

- **명시된 규약** — `README`, `CLAUDE.md`/`AGENTS.md`, `docs/`, ADR, 패키지 주석에 아키텍처 설명이 있는가.
- **이미 있는 아키텍처 테스트·린트 규칙** — 여기에 정답이 적혀 있으니 최우선으로 찾는다. ArchUnit/Konsist, `dependency-cruiser`, ESLint `import/no-restricted-paths`, `import-linter`, `deptrac`, Go `internal/` 패키지, Rust 모듈 가시성, `.editorconfig`/빌드 스크립트의 모듈 의존 선언.
- **빌드 모듈 경계** — 멀티모듈이면 `settings.gradle`·`pom.xml`·워크스페이스 설정의 모듈 간 의존 선언이 **이미 강제된 규칙**이다.
- **디렉토리·패키지 구조** — `domain`/`application`/`infrastructure`, `entities`/`usecases`/`adapters`, 기능별 슬라이스, 바운디드 컨텍스트 단위인지.
- **다수 관행** — 규약이 없으면 코드가 실제로 따르는 우세한 패턴을 규칙으로 삼는다.

**의도를 확정할 수 없으면 추론한 규칙을 먼저 제시하고 동의를 받은 뒤 검사한다.** 프로젝트가 채택하지도 않은 아키텍처를 기준으로 위반을 쌓아 올리는 것이 이 스킬의 가장 흔한 실패 방식이다.

확정한 규칙은 **허용 방향표**로 명시해 검사 시작 전에 보여 준다:

| 계층/모듈 | 참조해도 되는 대상 | 참조하면 안 되는 대상 |
|-----------|--------------------|------------------------|
| domain | (없음 — 자기 자신과 표준 라이브러리만) | application, infrastructure, 프레임워크 |
| application | domain | infrastructure 구현체, 웹/컨트롤러 |
| infrastructure | domain, application의 포트 | 컨트롤러 |
| presentation | application, (읽기 전용으로) domain | infrastructure 구현체 |

## 무엇을 검사하나 (언어 무관 체크리스트)

- **역방향 의존** — 안쪽(도메인)이 바깥쪽(인프라·웹·프레임워크)을 참조하는가. 가장 심각한 위반이며 1순위다.
- **계층 건너뛰기** — 컨트롤러가 서비스를 지나 저장소를 직접 호출하는 식의 skip-layer. 규약상 허용인지 먼저 확인한다(얇은 CRUD에서는 의도적 허용인 경우가 많다).
- **순환 의존** — 패키지·모듈·클래스 수준의 사이클. **사이클 전체 경로를 밝혀** 보고한다(`a → b → c → a`). 어느 한 간선을 끊어야 하는지가 핵심이다.
- **기술 누출** — 도메인 객체에 ORM/직렬화/웹 애노테이션이 붙었는가, ORM 엔티티가 API 응답으로 그대로 나가는가, 도메인 시그니처에 프레임워크 타입(HTTP 요청·세션·`ResultSet`)이 등장하는가.
- **추상화 방향 오류(DIP 미적용)** — 상위 계층이 하위 계층이 소유한 인터페이스에 의존하는가. 인터페이스는 **사용하는 쪽**이 소유해야 방향이 뒤집힌다. 인터페이스만 있고 구현이 하나뿐인데 패키지 위치가 하위에 있으면 방향은 여전히 바깥을 향한다.
- **모듈·컨텍스트 경계 침범** — 다른 바운디드 컨텍스트의 **내부 구현**을 직접 참조하는가(공개 API·이벤트가 아니라). 다른 모듈의 엔티티를 자기 트랜잭션에서 직접 다루는가.
- **공통 모듈의 역류** — `common`/`core`/`util`이 특정 도메인·상위 계층을 참조하는가. 공통 모듈은 항상 잎(leaf)이어야 한다.
- **전역 상태·양방향 참조** — 싱글턴·정적 홀더·서비스 로케이터로 방향을 숨기는가. 양쪽이 서로를 필드로 들고 있는가.
- **패키지와 실제 응집의 불일치** — 한 기능을 고치는 데 매번 여러 패키지를 동시에 만지는가(잘못된 분할 신호).

## 근거 규칙 (추정 금지)

- 위반은 **import/using/require 문과 파일 경로**라는 확인 가능한 사실로 지목한다. "결합도가 높아 보인다"는 근거가 아니다.
- 순환은 **경로 전체**를, 역방향 의존은 **어느 파일이 어느 파일을**인지를 밝힌다.
- 프로젝트에 **의존성 분석 도구가 이미 있으면 그것으로** 측정한다(ArchUnit, `dependency-cruiser`, `madge`, `import-linter`, `deptrac`, `go list`, `cargo tree`). 없으면 **임의로 도입하지 않고** import 문 조사로 검사한 뒤, 필요하면 도구 도입을 제안만 한다.
- 위반 **건수와 함께 위반의 중심**(가장 많이 얽힌 파일·패키지)을 제시한다. 100건이 흩어져 있는 것과 한 클래스에서 비롯된 것은 대응이 다르다.

## 영향도 산정

"**침범 깊이 × 확산 범위 × 대상의 핵심도**"로 가늠해 큰 것부터 정렬한다.

- 도메인이 인프라를 참조(가장 안쪽이 뚫림) > 컨트롤러가 저장소를 직접 호출(한 칸 건너뜀).
- 모듈 간 순환 > 같은 패키지 내 클래스 순환.
- 핵심 도메인의 위반 > 주변부 유틸의 위반.
- **한 곳만 고치면 여러 위반이 사라지는 지점**을 찾아 우선순위 맨 위에 올린다.

## 출력 형식

먼저 **판정 기준으로 삼은 허용 방향표**와 그 근거(어디서 왔는지: 문서/아키텍처 테스트/다수 관행/추론)를 밝힌다. 그다음:

| 위반 | 방향 | 위치 | 어긴 규칙 | 영향도 | 권장 조치 |
|------|------|------|-----------|--------|-----------|
| 역방향 의존 | domain → infrastructure | `Order.java:12` → `JpaOrderRepository` | domain은 infrastructure를 참조하지 않는다 | 상 | 포트 인터페이스를 domain에 두고 구현을 infrastructure로(DIP) |
| 순환 의존 | `order → payment → order` | `OrderService:40`, `PaymentService:88` | 모듈 간 순환 금지 | 상 | `payment → order` 간선을 도메인 이벤트로 대체 |

그리고 우선순위를 나눈다:

- **지금 고칠 것** — 안쪽을 뚫었거나 순환을 만드는, 방치하면 계속 번지는 위반.
- **나중에 해도 될 것** — 국소적이거나, 구조 변경 비용이 이득보다 큰 위반.
- **의도된 예외** — 규약상 허용이거나 합리적 트레이드오프인 것. 위반으로 세지 말고 **예외로 기록할 것을 제안**한다.

위반이 없으면 없다고 분명히 말한다. 억지로 항목을 채우지 않는다.

## 수정 (승인 후에만)

**이 스킬의 기본값은 검사다.** 구조 변경은 파급이 크고 되돌리기 어려우므로, 보고 후 사용자가 고르는 항목만 손댄다. 승인되면 다음 전략 중 하나를 명시하고 **한 번에 하나씩** 적용한다.

- **DIP로 방향 뒤집기** — 인터페이스(포트)를 사용하는 쪽(안쪽)으로 옮기고, 구현을 바깥에 둔다. 대개 가장 적은 이동으로 방향이 교정된다.
- **매핑 레이어 추가** — 도메인 객체와 영속·전송 객체를 분리해 기술 애노테이션을 도메인 밖으로 뺀다.
- **간선 끊기(순환)** — 사이클에서 **가장 약한 간선 하나**를 골라 이벤트·콜백·인터페이스 추출로 끊는다. 양쪽을 다 고치지 않는다.
- **공통 모듈 정리** — 역류하는 코드를 공통 모듈 밖으로 내보내 잎으로 되돌린다.
- **위치 이동** — 계층에 맞는 패키지로 옮긴다. 파일 이동은 diff가 커지므로 **다른 변경과 섞지 않고 이동만 하는 단위**로 분리한다.

## 절대 규칙

- **관측 가능한 동작과 공개 API를 바꾸지 않는다.** 방향 교정은 구조 변경이지 기능 변경이 아니다. 동작을 바꿔야만 가능한 개선이면 먼저 알린다.
- **대규모 이동을 한 번에 하지 않는다.** 위반 하나씩, 매번 빌드·테스트로 검증하고, 되돌리기 쉬운 커밋 단위로 나눈다.
- **테스트 코드와 DB 마이그레이션 파일은 명시적 지시 없이는 수정하지 않는다.** 아키텍처 테스트를 새로 추가해 규칙을 고정하는 것은 좋은 마무리지만, **추가 여부는 반드시 먼저 묻는다**(테스트 작업은 `test` 스킬 소관).
- **새 분석 도구·린트 플러그인을 임의로 도입하지 않는다.** 제안만 한다.
- **채택되지 않은 아키텍처를 강요하지 않는다.** 작은 CRUD 서비스에 헥사고날을 들이대 위반 목록을 만드는 것은 도움이 아니라 소음이다. 규칙의 출처를 항상 밝힌다.
