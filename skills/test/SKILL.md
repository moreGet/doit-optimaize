# 테스트 현행화 · 커버리지

이 스킬은 다른 스킬들의 "테스트는 명시적 지시 없이 수정하지 않는다" 규칙에 대한 **명시적 지시 경로**다.
즉 여기서는 테스트를 고치고 추가할 수 있다. 대신 **프로덕션 코드는 건드리지 않는다** — 방향이 정반대다.

## 0단계: 환경 파악 (항상 먼저)

무엇을 하든 아래를 먼저 확인한다. 추정으로 명령어를 만들어 실행하지 않는다.

- **빌드·실행 도구** — Gradle/Maven, npm/pnpm/yarn, uv/poetry/pip, go, cargo, dotnet 등. 매니페스트(`build.gradle`, `pom.xml`, `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`)에서 확인한다.
- **테스트 프레임워크** — JUnit5/Kotest/Spock, pytest/unittest, Jest/Vitest/Mocha, go test, xUnit 등. 의존성과 기존 테스트 파일 양쪽으로 교차 확인한다.
- **테스트 위치·명명 규칙** — `src/test/java/...`, `tests/`, `__tests__/`, `*_test.go`, `*.spec.ts`. 새 파일은 **기존 규칙 그대로** 놓는다.
- **커버리지 도구** — JaCoCo/Kover, pytest-cov, c8/nyc/`--coverage`, `go test -cover`, coverlet 등. 이미 설정돼 있으면 그 설정을 쓴다.
- **실행 명령** — CI 설정(`.github/workflows`, `Jenkinsfile`)이나 스크립트에 정의된 **공식 명령**을 찾아 그대로 쓴다.
- **레이어 구조** — 패키지·디렉토리로 API/컨트롤러/서비스/도메인이 어떻게 나뉘는지, 프로젝트가 실제로 쓰는 이름은 무엇인지(`application`, `usecase`, `repository` 등).

파악 결과를 한 줄로 요약해 보고한 뒤 다음 단계로 간다.

## 분기 A — 테스트가 이미 있는 경우: 현행화

1. **현재 상태 측정** — 공식 명령으로 테스트를 먼저 돌려 **손대기 전의 실패 목록**을 확보한다. 원래 깨져 있던 것과 내가 깬 것을 구분하기 위한 기준선이다.
2. **낡은 테스트 식별** — 아래를 찾는다.
   - **실패하는 테스트** — 구현이 바뀌어 기대값이 낡은 것 vs **실제 버그를 잡아낸 것**을 구분한다. 후자는 고치지 말고 보고한다.
   - **건너뛴 테스트** — `@Disabled`/`skip`/`xit`/`t.Skip`. 왜 꺼졌는지 확인하고 되살릴 수 있으면 되살린다.
   - **컴파일·임포트가 깨진 테스트** — 시그니처·패키지 변경을 따라가지 못한 것.
   - **죽은 테스트** — 사라진 코드를 검증하는 테스트.
   - **의미 없는 테스트** — 단언이 없거나(`assert` 없음), 모킹한 것을 그대로 다시 확인하는 자기충족 테스트, 항상 참인 단언.
   - **불안정(flaky) 테스트** — 시간·순서·난수·외부 네트워크에 의존하는 것. 고정 시계·시드·스텁으로 결정론적으로 만든다.
3. **현행화** — 테스트를 **현재 구현의 계약에 맞게** 고친다. 기존 테스트의 스타일(픽스처·네이밍·given/when/then·모킹 라이브러리)을 그대로 따른다.
4. **재실행** — 전부 통과하는지, 기준선 대비 새로 깨진 것이 없는지 확인한다.
5. **커버리지 측정** — 아래 "커버리지" 절대로 측정하고 보고한다.
6. **구멍 보고** — 커버리지가 낮은 지점 중 **위험도가 높은 것**(분기 많은 도메인 로직, 예외 경로, 최근 변경분)을 우선순위로 제시한다. 보강 테스트를 새로 추가할지는 사용자에게 묻고 진행한다.

## 분기 B — 테스트가 없는 경우: 추가 여부·범위 확인

**임의로 테스트를 만들지 않는다.** 0단계 환경 파악 결과를 근거로 판단하고 확인을 받는다.

1. **환경 적합성 판단** — 테스트를 추가할 준비가 돼 있는지 먼저 본다.
   - 테스트 프레임워크 의존성이 있는가? 없다면 **새 의존성 추가가 필요**하다는 사실을 명확히 알린다(이것도 승인 대상).
   - 테스트 실행이 가능한 환경인가(빌드 통과, DB·외부 의존성 필요 여부)?
   - 테스트를 붙일 만한 구조인가? 결합도가 높아 테스트하려면 프로덕션 코드 수정이 불가피하다면, **그 사실을 먼저 알린다**(이 스킬은 프로덕션 코드를 고치지 않는다).
2. **범위 확인 (질문)** — 아래 선택지를 제시해 사용자에게 묻는다. 답을 받기 전에는 파일을 만들지 않는다.

   | 범위 | 대상 | 특징 |
   |------|------|------|
   | **API 레이어만** | 외부에 노출된 계약(HTTP/RPC 엔드포인트) | 통합·E2E 성격. 사용자 시나리오를 실제 요청/응답으로 검증. 느리지만 회귀 방어가 가장 넓다 |
   | **컨트롤러 레이어만** | 요청 매핑·검증·직렬화·상태코드 | 하위 계층은 모킹. 입력 검증과 응답 형식 회귀에 강하다 |
   | **서비스 레이어만** | 유스케이스·트랜잭션 흐름·오케스트레이션 | 저장소·외부 연동은 모킹. 비즈니스 흐름 검증에 가성비가 가장 좋다 |
   | **도메인 레이어만** | 엔티티·값 객체·도메인 규칙·계산 | 의존성 없이 순수 단위 테스트. 가장 빠르고 안정적 |
   | **전부** | 위 전체 | 시간·분량이 가장 크다. 레이어별로 나눠 단계적으로 진행 |

   판단 근거가 있으면 **추천안을 함께 제시**한다(예: "도메인 규칙이 두껍고 컨트롤러는 얇으니 도메인 → 서비스 순을 권합니다").
3. **승인 후 작성** — 확정된 범위에서만 만든다. 한 번에 전부 쏟아내지 말고 대표 케이스부터 만들어 **실제로 통과하는 것을 확인한 뒤** 확장한다.
4. **실행·커버리지 측정 후 보고.**

## 무엇을 테스트하나 (좋은 테스트 기준)

- **계약을 검증한다** — 내부 구현이 아니라 관측 가능한 동작(반환값·부수효과·예외)을. 구현을 조금 바꿨다고 깨지는 테스트는 부채다.
- **경계와 예외 경로를 덮는다** — 정상 경로만 덮은 테스트는 커버리지 숫자만 올린다. 빈 값·null·0·음수·최대치·중복·동시성·실패 응답을 우선한다.
- **하나의 테스트는 하나를 검증한다** — 이름만 보고 무엇이 깨졌는지 알 수 있어야 한다. 기존 네이밍 규칙을 따른다.
- **결정론적이어야 한다** — 현재 시각·난수·실행 순서·네트워크에 의존하지 않는다.
- **독립적이어야 한다** — 테스트 간 상태를 공유하지 않는다.

## 커버리지

- 프로젝트에 **설정된 도구가 있으면 그것으로** 측정한다. 없으면 임의로 도입하지 말고, 어떤 도구를 어떻게 추가할지 **제안하고 승인을 받는다.**
- 보고는 수치와 함께 **어디가 비었는지**를 함께 낸다:

  | 대상 | 라인 | 분기 | 비어 있는 핵심 경로 |
  |------|------|------|---------------------|
  | OrderService | 72% | 55% | 결제 실패 롤백 분기, 재고 부족 예외 |

- **숫자를 목표로 삼지 않는다.** 커버리지를 올리려고 단언 없는 테스트나 게터/DTO 테스트를 찍어내지 않는다. 덮이지 않은 것 중 **위험한 것**만 우선순위로 올린다.
- 커버리지 임계치(CI gate)가 설정돼 있으면 그 기준을 기준선으로 삼아 통과 여부를 보고한다.

## 절대 규칙

- **프로덕션 코드를 고치지 않는다.** 테스트가 실제 버그를 잡았다면 테스트를 기대값에 맞춰 고치는 게 아니라 **버그로 보고**한다. 테스트를 위해 프로덕션 코드 변경이 필요하면 무엇을 왜 바꿔야 하는지 제안하고 승인을 받는다.
- **실패를 숨기지 않는다.** 통과시키려고 단언을 약하게 만들거나, 테스트를 비활성화하거나, 예외를 삼키지 않는다. 못 고친 실패는 실패로 보고한다.
- **DB 마이그레이션 파일은 명시적 지시 없이 수정하지 않는다.**
- **새 의존성·설정 변경은 승인을 받는다.** 테스트 프레임워크, 모킹 라이브러리, 커버리지 플러그인 모두 해당한다.
- **기존 테스트 컨벤션을 따른다.** 새 스타일을 들여와 두 가지 방식이 공존하게 만들지 않는다.

## 출력

1. **환경 요약** — 빌드 도구·테스트 프레임워크·커버리지 도구·실행 명령.
2. **분기와 계획** — A(현행화) / B(신규, 범위 확인)인지와 무엇을 할지.
3. **작업 결과** — 무엇을 고치거나 추가했는지, 실행 결과(통과/실패 수)를 기준선과 대비해서.
4. **커버리지 표**와 위험도 순 보강 제안.
5. **미해결 항목** — 못 고친 실패, 실제 버그로 의심되는 것, 승인이 필요한 사항.
