# 로그 레벨 배치 (프로젝트 패턴 준수)

좋은 로그의 기준은 양이 아니라 **장애가 났을 때 원인을 재구성할 수 있는가**이다.
이 스킬은 두 가지를 동시에 지킨다 — (1) 레벨을 의미에 맞게 쓰고, (2) **이 프로젝트가 이미 쓰고 있는 로깅 관용구를 그대로 따른다.**
주변과 이질적인 로그는 아무리 잘 짜도 검색·집계·알림 파이프라인에서 깨진다.

## 진행 순서

1. **기존 패턴 학습 (반드시 먼저)** — 코드를 고치기 전에 이 프로젝트의 로깅 방식을 조사한다. 조사 없이 로그를 추가하지 않는다.
2. **범위 확정** — 인자가 있으면 그 대상, 없으면 `git diff`(스테이징 포함)로 현재 변경분을 대상으로 한다.
3. **후보 수집** — 아래 "어디에 남기나 / 무엇을 덜어내나"로 누락·과잉 지점을 나열한다.
4. **레벨 판정** — 각 지점을 레벨 기준표에 비춰 판정한다. 애매하면 낮은 레벨(INFO→DEBUG) 쪽으로 보수적으로 잡는다.
5. **수정** — 학습한 관용구 그대로 적용한다. 새 로깅 방식이나 새 의존성을 임의로 도입하지 않는다.
6. **검증** — 프로젝트 테스트 스위트로 회귀가 없음을 확인한다. 로그 문자열을 검증하는 테스트가 있으면 특히 주의한다.

## 1단계: 무엇을 학습하나 (필수 선행 조사)

- **로깅 수단** — 프레임워크/라이브러리는 무엇인가(SLF4J·Logback·Log4j2, `logging`, `zap`/`slog`, `winston`/`pino`, `Serilog` 등). `print`/`console.log` 계열이 섞여 있다면 어느 쪽이 정식인가.
- **로거 획득 관용구** — 클래스별 정적 로거인가, 애노테이션(`@Slf4j`)인가, 모듈 스코프 로거인가, DI로 주입받는가. **주변 파일과 똑같은 방식**을 쓴다.
- **메시지 스타일** — 언어(한국어/영어), 대소문자, 접두어(`[OrderService]`), 파라미터화 방식(`{}` / `%s` / f-string / 템플릿 리터럴).
- **구조적 로깅 여부** — key=value·JSON 필드로 남기는가(MDC, `logger.info("...", extra={...})`, `zap.String(...)`). 구조적 로깅을 쓰는 프로젝트에서 문자열 접합으로 남기면 안 된다.
- **상관관계 ID** — traceId·requestId·userId 같은 추적 키를 어떻게 싣는가. 이미 컨텍스트가 있으면 반드시 함께 남긴다.
- **마스킹·민감정보 규칙** — 기존에 마스킹 유틸이 있는가. 있으면 그것을 쓴다.
- **레벨 운영 정책** — 설정 파일에서 운영 환경의 기본 레벨은 무엇인가. 운영이 INFO면 DEBUG 로그는 평시에 보이지 않는다는 전제로 배치한다.

조사 결과 관용구가 **일관되지 않으면**, 임의로 통일하지 말고 다수 패턴을 따르되 불일치 사실을 보고한다.

## 2단계: 레벨 기준표

| 레벨 | 판단 기준 | 전형적 위치 |
|------|-----------|-------------|
| **ERROR** | 처리에 실패했고 **사람의 개입·조사가 필요**한 사건. 알림이 울려도 이상하지 않은 것만. | 복구 불가 예외, 외부 연동 최종 실패, 데이터 정합성 위반, 미처리 예외 핸들러 |
| **WARN** | 실패는 아니지만 **비정상이며 방치하면 문제**가 되는 신호. 스스로 복구했지만 기록은 남겨야 하는 것. | 재시도 후 성공, 폴백 경로 진입, 만료 임박·임계치 근접, 사용 중단 API 호출, 예상 못한 입력을 기본값으로 대체 |
| **INFO** | **비즈니스적으로 의미 있는 사건**의 기록. 평시 운영 로그로 남아 흐름을 재구성할 수 있는 것. 요청당 몇 건 수준. | 주문 생성·결제 승인·상태 전이, 배치 시작/종료와 처리 건수, 애플리케이션 기동·설정 로드, 외부 시스템 호출 결과(요약) |
| **DEBUG** | 개발·장애 분석 때만 필요한 **내부 흐름과 중간값**. 운영에서 꺼져 있어도 되는 것. | 분기 결정 근거, 조회 조건과 결과 건수, 캐시 히트/미스, 계산 중간 결과 |
| **TRACE** | 매우 상세한 추적(있는 프로젝트에서만 사용). | 루프 내부 단계, 페이로드 전문 |

판정이 애매할 때의 기준:

- "이 로그를 보고 **누군가 조치해야 하나?**" → 예면 ERROR, 아니면 WARN 이하.
- "**운영에서 평시에 켜 둬도** 양과 가치가 맞나?" → 아니면 DEBUG.
- "**비즈니스 사건**인가, 내부 구현 세부인가?" → 후자면 DEBUG.

## 3단계: 어디에 남기나

- **경계** — 외부에서 들어오고 나가는 지점(요청 수신·응답, 메시지 소비, 배치 진입/종료). 진입 파라미터 요약과 결과·소요 시간.
- **외부 연동** — DB 외 API·큐·파일 시스템 호출의 결과, 재시도, 타임아웃. 실패는 대상·상태코드·소요 시간을 함께.
- **상태 전이** — 도메인 객체의 의미 있는 상태 변화(결제 대기 → 승인). INFO의 1순위.
- **예외 처리** — `catch` 지점. 예외를 삼킨다면 반드시 로그가 있어야 하고, **스택트레이스를 예외 객체째로 넘긴다**(메시지 문자열만 남기지 않는다).
- **비자명한 분기** — 왜 이 경로로 갔는지 나중에 알 수 없는 조건 분기의 근거(DEBUG).

## 4단계: 무엇을 덜어내나

- **중복 로깅** — 같은 예외를 계층마다 `log` + `throw`로 반복해 남기는 패턴. **처리하는 곳에서 한 번만** 남긴다.
- **루프 내부 로그** — N에 비례해 폭발한다. 요약(건수·실패 목록)으로 대체하거나 DEBUG/TRACE로 내린다.
- **의미 없는 로그** — `"start"`, `"here"`, `"=== 1 ==="`, 값 없는 진입/이탈 로그.
- **레벨 오용** — 정상 흐름의 ERROR(알림 피로), 장애 분석에 꼭 필요한데 DEBUG로 묻힌 사건.
- **디버깅 잔재** — `print`/`console.log`/임시 덤프. 정식 로거로 바꾸거나 제거한다.

## 절대 규칙

- **민감정보를 원문으로 남기지 않는다.** 비밀번호·토큰·인증 헤더·주민번호·카드번호·계좌·전화번호·이메일·주소 등. 기존 마스킹 유틸이 있으면 사용하고, 없으면 식별자(ID)만 남기거나 마스킹 필요성을 보고한다. **페이로드·엔티티 전체를 통째로 찍지 않는다.**
- **로그가 동작을 바꾸지 않는다.** 로깅을 위해 추가 쿼리·원격 호출을 하지 않고, 컬렉션을 강제로 로딩하지 않으며(지연 로딩 주의), 로깅 코드에서 예외가 새어 나가지 않게 한다.
- **뜨거운 경로에서는 비용을 낸다는 사실을 인지한다.** 파라미터화된 메시지를 쓰고(문자열 접합 금지), 인자 계산이 비싸면 레벨 가드(`isDebugEnabled` 등 프로젝트 관용구)를 쓴다.
- **테스트 코드와 DB 마이그레이션 파일은 명시적 지시 없이는 수정하지 않는다.**
- **새 로깅 라이브러리·설정 파일을 임의로 도입하지 않는다.** 필요하다고 판단되면 제안만 한다.

## 출력

수정 **전에는** 학습한 관용구(로거 획득 방식·메시지 포맷·구조적 필드)를 한 줄로 요약하고, 아래 표로 제안을 제시해 동의를 받는다:

| 위치 | 현재 | 제안 레벨 | 이유 |
|------|------|-----------|------|
| file:line | 없음 / ERROR / print | INFO | 결제 상태 전이 — 사후 추적에 필요 |

수정 **후에는** 아래 최종 리포트만 남긴다.

## 최종 리포트 (형식 고정)

작업이 끝나면 **결론 한 줄 + 표**로만 보고한다. 과정 설명·산문 문단을 덧붙이지 않는다.

**결론 한 줄** — 로그를 몇 건 넣고 몇 건 덜어냈는지.

| 실행 | 대상 | 따른 관용구 | 결과 | 검증 |
|------|------|-------------|------|------|
| `/optimize:logging <받은 인자 그대로>` | 파일 3개 | `@Slf4j` 정적 로거 + `{}` 파라미터화 + MDC `traceId` | 추가 4건, 레벨 조정 2건, 제거 3건 | 테스트 96건 통과, 실패 0 |

| # | 위치 | 한 일 | 레벨 | 이유 |
|---|------|-------|------|------|
| 1 | `PaymentService.java:71` | 로그 추가 | INFO | 결제 승인 상태 전이 |
| 2 | `OrderRepository.java:44` | ERROR → DEBUG | DEBUG | 정상 폴백 경로, 조치 불필요 |

- 마스킹 유틸 부재처럼 **결정이 필요한 사안**은 임의로 정하지 말고 여기에 한 줄씩 최대 3개로 올려 묻는다. 없으면 이 불릿을 생략한다.

인자 없이 호출됐으면 `실행` 칸은 `/optimize:logging (인자 없음 → git diff)`처럼 **실제 판단 기준을 그대로** 적는다.
